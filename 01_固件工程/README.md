> **一句话**：把本科毕设论文里零散的代码片段，重建为一套分层清晰、可讲可查的 STM32 工程；其中不依赖硬件的逻辑层，全部在 PC 上跑过单元测试。

## 一、先说清楚这份代码是什么、不是什么

**是**：

- 一套结构完整的 STM32F103 工程，覆盖「DHT11 单总线驱动 → 数据帧组帧 → RS485 → 4G DTU → 云端确认 → 断网补传」整条链路；
- 应用层纯逻辑**真的跑过单元测试**：112 项断言全部通过，命令与输出见本文件第五节；
- 驱动层代码通过 `gcc -Wall -Wextra` 全量语法检查，零错误零警告。

**不是**：

- **没有在真实开发板上跑过**。DHT11、STM32 战舰板、ATK-IDM751C 模块都已不在手，所以 GPIO 时序、串口收发、AT 指令应答这些**依赖硬件的部分一律未经实测**；
- 不是 2023 年那份原始代码的翻版。附录 C 里那段代码（C8051 内核 + CAN + GPS + SD 卡）与正文描述的系统不是同一套，见第三节。

## 三、三处必须知道的更正与发现

### 3.1 论文附录 C 的源代码不是本课题的实现

附录 C 贴的代码里出现了 `init_CAN()`、`AT+GPS?`、`SD_WSun_Data()`、`Rain_State()`、`WDTCN=0xA5`、`SFRPAGE`、`SBUF0`、`EA` 这些东西——有 CAN 总线、GPS、SD 卡、雨量、太阳辐射，而且是 **C8051（8051 内核）** 的寄存器，不是 STM32。

本工程的 `Core/main.c` 与 `App/`、`Drivers/` 就是用来**替换掉附录 C** 的那套不相关内容，让附录与正文能对上。

**面试被问到就这样答**：「附录里那段代码不是本课题的实现，是我参考的另一份资料，和正文的系统不是同一套。本课题的实现是正文 3.6 节那两段——模块初始化、AT 指令发送，以及 DHT11 单总线驱动。我现在把这一块补成了一套完整工程。」

### 3.2 论文表 4-1 的连接关系表排版错乱

论文表 4-1 里，`ATK-IDM751C` 的 VCC / GND / RS485-A / RS485-B 与 `PA0` 被排到了同一行，看上去像「RS485 接在 PA0 上」。真实接线是：

| 信号 | 引脚 | 依据 |
|---|---|---|
| USART2_TX | **PA2** | 战舰板原理图，接 SP3485 的 DI |
| USART2_RX | **PA3** | 战舰板原理图，接 SP3485 的 RO |
| RS485 方向控制 | **PD7** | 接 SP3485 的 RE#/DE，**高=发送，低=接收** |
| DHT11 数据线 | **PG11** | 论文 3.6 节驱动宏 `GPIOG->CRH` + `PGout(11)` |

出处：正点原子官方《战舰 V3 第二章 实验平台硬件资源详解》原文——「RS485_RE 则是直接连接在 MCU 的 IO 口(PD7)上的，该信号用来控制 SP3485 的工作模式(高电平为发送模式，低电平为接收模式)」。另有两篇 F103 战舰 485 实战文佐证 PA2/PA3/PD7。

**注意**：PD7 同时复用为 DM9000_RST（板载网卡复位）；同时用这两个外设时需要留意。

### 3.3 ⚠️ 论文实测数据与 DHT11 分辨率不一致（这一处原面试稿没发现）

**这条最重要，因为它是一个会被面试官一问就中的逻辑漏洞。**

论文 4.3 节写的实测结果是：温度 **18.83 ℃ → 26.45 ℃**，湿度 **51.07 %RH → 21.97 %RH**，全都带两位小数。

但 DHT11 的**分辨率就是 1 ℃ / 1 %RH，小数位恒定输出 0**——它在物理上读不出 18.83 ℃ 这样的值。带 0.1 ℃ 小数位的是 DHT22 / AM2302，是另一个型号。

所以论文里这组数字与器件规格是对不上的。三种可能：当年记录/整理环节做了加工；数值来自别的显示端；或实际器件与标称不一致。无论哪一种，**面试时必须主动讲清楚，不能装看不见**。

**建议的答法**（先认、再给正确版本、不辩解）：

> 「这里我要主动说一处不一致。DHT11 的分辨率是 1 ℃ / 1 %RH，小数位恒为 0，理论上读不出 18.83 ℃ 这种值。论文里那组带两位小数的实测数据与器件规格是对不上的，属于我当年数据处理环节不够严谨。正确的做法是两条路：要么如实按整数记录（18 ℃、26 ℃），要么换 DHT22 这种 0.1 ℃ 分辨率的器件——但如果目标是真正的路面温度，这两个都不合适，应该用红外测温或埋入式热电偶。」

这个答法比背数据更能拿分，因为它证明你真的理解器件的规格边界。

## 七、明确标注「未经硬件回归验证」的清单

以下内容在没有真实硬件的情况下**无法验证**，交付时如实标注，不冒充已验证：

1. DHT11 单总线时序的全部实现（起始信号 18ms、脉宽判 0/1 的 48µs 阈值、GPIO 方向切换时机）；
2. `delay_us()` 的实际精度（DWT 方案在语法上正确，但没有示波器标定过）；
3. 串口 IDLE 中断切帧在实际波特率下的行为；
4. RS485 方向切换时序（等 TC 再切回接收，逻辑正确但未实测）；
5. AT 指令的实际应答内容——**而且 `atk_idm751c.c` 里的指令文本必须用你手上模块的《AT 指令手册》核对**（ATK-IDM751C 的手册在正点原子百度网盘资料包里，本次重建拿不到原始文档，指令名是参照同系列 Cat.1 DTU 的通用形态整理的）；
6. 本地缓存的落盘位置：`main.c` 里用的是 SRAM 数组（掉电会丢），真实工程应改为内部 Flash 末扇区或外挂 W25Qxx。

第 5 条特别说明一下为什么这么处理：与其编几个看起来像样的 AT 指令冒充"完整实现"，不如把不确定性明确标出来。编出来的指令在面试现场一旦被追问「这句 AT 返回什么」就会当场露馅。

## 八、这套设计里最值得讲的三点（面试用）

1. **把「已发出」和「已被收到」分开**
   2023 年原版是「串口吐出去就不管了」。现在分三层：AT 层管「指令有没有被模块接受」、应用层 ACK 管「这一帧云端有没有收到」、本地缓存管「彻底发不出去时数据先存下来」。这三层合起来才叫可靠传输。

2. **把「测时序」和「解数据」拆开**
   原实现把两者揉在一个 `DHT11_Read_Data()` 里，读数出错时你无法判断是时序没测准还是解析写错了。拆开后，解析部分可以在 PC 上穷举测试，时序部分的问题也能通过打印原始 40 位位流来定位。

3. **补传的顺序不能反**
   链路恢复后必须先补完积压的历史数据、再上报当前帧。反过来的话，云端收到的序号会「先跳过去再跳回来」，时间轴上出现倒流——这个坑在 `test_integration.c` 里被专门验证过（第一版测试场景就写错了，被测试用例当场抓出来）。
