路线 A · 零硬件¥0
跑 PC 端的单元测试（112 项断言）+ 打开演示页。这是当前状态，也是零成本就能验证的一步—— 把这两个东西跑一遍，就能对「系统怎么工作」有比文字描述更清楚、更具体的把握。
路线 B · 最小闭环约 ¥30–80
STM32 最小系统板 + DHT11，串口打印温湿度。能验证 DHT11 单总线驱动是否真的写对了 （这一步在真实硬件上最容易被时序问题绊住）。4G 那一段用串口助手手工模拟。
路线 C · 完整复现约 ¥150–350
在 B 的基础上加 4G Cat.1 DTU + 流量卡 + 云端账号，把「采集 → 上云 → 上位机」整条链路重新跑通， 并用拔天线的方式实测断网补传。这是唯一能让「补传」从代码变成实测记录的路径。
路线 D · 技术升级版再加 ¥60–300
把传感器从 DHT11 换成红外测温模块，解决「测的不是路面温度」这个根本问题—— 这是整个课题里最该改的一处。见第 1 节。
建议：如果只是要在软件层面把项目读懂、跑起来，走路线 A 就够了，不必花钱。 如果确实要把这个项目做成能上真机的完整作品，走 B → C，约 2–3 个周末。 路线 D 是加分项，但会让周期变长，建议先跑通 C 再考虑。

1技术选型：哪一块该改、哪一块不用改

先说结论：主控、通信、云端这三块当年选得都对，不用改；唯一该改的是传感器。

环节2023 原方案现在建议理由
温度传感器 DHT11
测量的是空气		 红外测温 MLX90614
或埋入式热电偶		 这是唯一必须改的一块。DHT11 测的是近地表空气温湿度，不是路面温度； 而且量程只有 0–50 ℃，夏季沥青路面常超 60 ℃，已经出量程。这正是论文绪论里分析过的 「接触式 vs 非接触」两条路，当年因为成本和实现难度选了折中方案。
主控 STM32F103（战舰板） 不改 72 MHz 主频、5 个 USART、足够的外设与 GPIO，跑这套逻辑绰绰有余。换芯片没有任何收益。

云平台 正点原子云 不改（单点） 设备注册、数据转发、可视化的功能已经够用，且免费。

如果走路线 D：红外测温的两个坑

坑一：发射率（emissivity）。MLX90614 出厂按 ε = 1.0（理想黑体）标定。 沥青路面的 ε 大约在 0.95 附近，测出来会有偏差；如果是光亮的金属表面（ε 只有 0.05–0.10）， 那测到的根本不是它自己的温度，而是环境在它表面的反射。解决办法：要么在传感器 EEPROM 里 改写 ε 系数，要么在被测表面贴一小块哑光黑胶带做定标。
坑二：视场角（FOV）。MLX90614 有 90° / 35° / 10° / 5° 等不同视场角的型号， 它测的是视场范围内温度的平均值。装在路边斜着打路面，不同 FOV 意味着测到的面积差别很大—— 选型时要按实际安装高度和角度算一下覆盖面积。

另外提醒一句：红外测温的精髓是「知道发射率才能把辐射能量反演成真实温度」。 这一点论文绪论第 1.2 节已经讲到了（非接触测温靠测量红外辐射逆温）， 重做时能把它落到参数上，就说明你真的读懂了那一节。

4时间对照与三个省力杠杆

里程碑硬做用本指南省在哪
逻辑验证等硬件到货才能开始阶段 0，随时可做逻辑已经抽出来测过了，硬件只是最后一公里的验证
DHT11 驱动调通1–3 天（时序问题很难查）半天驱动宏与原论文一致，且 40 位解析部分已在 PC 上测过，问题范围缩小一半
4G 上云2–3 天（AT 指令试错）1 天先用 USB 转 RS485 单独把 DTU 调通，再挂到 MCU 上
补传功能1–2 天（顺序容易写反）半天「先补历史再上新的」这个顺序坑已经被测试用例标出来了

三个省力杠杆

  • 杠杆一：先用串口助手把模块单独调通。不要一上来就把 DTU 挂在 MCU 上调试。 分开调能把「是模块的问题」和「是我代码的问题」这两件事隔离开，排查时间至少减半。
  • 杠杆二：把「逻辑」和「硬件」分开验证。数据帧、校验、缓存、重传这些逻辑 已经能在 PC 上跑测试；上真机时只需要关注 GPIO 时序和串口电平。问题范围小了，速度就快了。
  • 杠杆三：断网用拔天线模拟，不要改代码。在代码里加一个 if (force_offline) 来模拟断网， 验证的是你的代码；拔天线验证的是整条链路。后者才是实测证据。

5三条必须记住的诚实权衡

第一，换传感器解决的是「测得对不对」，不是「传得稳不稳」。 项目的顺序应该是：先解决测量对象与标定，再解决传输与可靠性，而不是反过来。 如果只有时间做一件事，做前者——因为「测的不是路面温度」是题目与实现之间最根本的一处不匹配。
第二，没有标准仪器比对，就没有「精度」可谈。 这套系统能证明的是「链路可行」，不是「测量准确」。 要谈精度，必须补上「与标准仪器比对」这一步——这是从「做出来」到「做对」的分界线。
第三，补传功能写出来容易，写对不容易。 三个最容易错的地方：恢复后先补历史还是先上新的（顺序）、缓存满了丢最旧还是丢最新（策略）、 重复 ACK 要不要当错误处理（不该）。这三个点在本工程的测试用例里都有对应验证。
