## 这是什么

2023 年的本科毕设：把远端道路的温湿度采上来、经 4G 传回云端。当年留下的只有一份论文、正文 3.6 节的两段代码，以及附录 C 里一段与正文对不上、来源不同的源码。

2026 年复盘时做了两件事：

1. **把论文里的碎片重建成一套分层完整的工程** —— 采集、组帧、传输、确认、补传各有归属，不再揉在一个函数里；
2. **补上原设计里缺失的可靠性设计** —— 数据帧 CRC16 校验、断网本地缓存、重传与 ACK 确认、补传顺序保证。

> 需要说明的是：这四项**论文里一个字都没提**。全文检索「断网 / 补传 / 重传 / CRC / 校验和 / 数据一致性」，出现次数均为 0。
> 它们是复盘时新加的，源文件头部一律标 🔵`[2026 复盘补做]`。论文「结论与展望」里真正列出的后续工作
> 是另一批东西，且至今仍未做 —— 见下面「五条硬边界」第 5 条。

## 五条硬边界

这五条我主动写在这里，不留着等面试官发现。

**1. 没在真实硬件上跑过**

DHT11、战舰 STM32F103 板、ATK-IDM751C 模块都已不在手。所以 GPIO 时序、串口收发、AT 指令应答这些**依赖硬件的部分一律未经实测**。已做到的验证是：应用层纯逻辑 112 项断言全过、驱动层 `gcc -Wall -Wextra` 零错误零警告、AT 指令文本明确标注「须以手上模块手册核对」。

**2. 论文附录 C 的源码不是本课题的实现**

附录 C 里出现了 `init_CAN()`、`AT+GPS?`、`SD_WSun_Data()`、`SFRPAGE`、`SBUF0` —— 有 CAN 总线、GPS、SD 卡、雨量、太阳辐射，而且是 **C8051（8051 内核）** 的寄存器。本工程就是用来**替换掉附录 C** 的那套不相关内容，让附录与正文能对上。

**3. 论文表 4-1 的连接关系表排版错乱**

表里 `ATK-IDM751C` 的 VCC/GND/RS485-A/RS485-B 与 `PA0` 被排到了同一行，看上去像「RS485 接在 PA0 上」。真实接线是 **USART2（PA2/PA3）+ PD7 做方向控制**（高电平发送、低电平接收），出处为正点原子《战舰 V3 实验平台硬件资源详解》。本工程按真实接线实现。

**4. 论文实测数据与 DHT11 分辨率不一致（这一处原口述稿未发现）**

论文 4.3 节写实测温度 `18.83 → 26.45 ℃`、湿度 `51.07 → 21.97 %RH`，都带两位小数。但 **DHT11 的分辨率就是 1 ℃ / 1 %RH，小数位恒为 0**，物理上读不出 18.83 这种值；带 0.1 ℃ 的是 DHT22。

这不是用词不严谨，是一个**一问就中**的点。正确答案是：DHT11 的分辨率就是 1 ℃ / 1 %RH，那组两位小数的数据物理上读不出来；带 0.1 ℃ 分辨率的是 DHT22 / AM2302，属另一个型号。被问到时如实说明这一处不一致，不做辩解。

**5. 论文「结论与展望」真正列出的后续工作，一项都还没做**

上面第 2 条说到论文全文没提过断网补传 —— 那论文展望里写的是什么？原文是：

> 目前仅开展了道路单点短时间的温度采集试验……后续还需要通过**多频次、多地点的试验**，分析**测量数据不稳定、路面交通复杂无法排除其他干扰**等影响，**提高试验精度**，并**通过与标准设备的比对**，来验证本设计的适用性与准确性，为**三维动态监测**道路温度提供技术基础。

也就是说，论文自己列的四项后续工作是：多频次多地点试验、数据不稳定与干扰分析、与标准设备比对、三维动态监测。**这四项至今仍未做**，而且性质是「把实验做全」，不是「把代码补全」——不是复盘时坐在电脑前能补的，需要真实场地与标准仪器。

此外任务书 1.4 要求「开展道路温度、**定位信息**的远程动态接收与解析」，实测只回传了时间与温湿度，**定位未落地**。

把这一条写出来是有意的：面试官如果真翻过论文，他问的会是「多点试验做了吗」「和标准设备比对过吗」，而不是 CRC。这两个问题必须提前有答案。

## 关于测温对象的边界（选读）

原始设计的测温对象其实**不是路面**，而是**近地表空气温湿度** —— DHT11 是空气温湿度传感器，装在路侧只能反映近地表空气状态，受日照、通风、安装高度影响很大。

论文里把它当作道路温度来写，是这处设计最需要说清的地方。要真正测路面温度，应该用红外测温（如 MLX90614）或埋入式热电偶，并做标准仪器比对。升级路径写在 `03_项目复现指南/`。
